# 03_ROOT_CAUSE_ANALYSIS.md - 근본 원인 분석

## 관측된 증상

### 증상 1: 라우팅 결정 불투명성
**설명**: Sisyphus Router가 쿼리를 분석하여 Low/Normal/High Sisyphus 중 하나로 라우팅하지만, 그 결정 과정이 사용자에게 표시되지 않음

**증상 세부사항**:
```
사용자 쿼리 → [블랙박스] → "High Sisyphus가 작업을 시작했습니다"
               ↑ 어떤 분석이 이루어졌는지 알 수 없음
```

### 증상 2: 디버깅 어려움
**설명**: 라우팅이 잘못된 경우 (예: 복잡한 쿼리가 Low Sisyphus로 라우팅), 문제 원인을 파악할 수 없음

**증상 세부사항**:
- 라우팅 로직 디버깅 불가
- 사용자 불신 유발
- 최적화 기회 상실

### 증상 3: 정보 비대칭
**설명**: AI 시스템은 쿼리 복잡도를 분석하지만, 사용자는 그 분석 결과를 알 수 없음

## 재현 조건

### 조건 1: 기본 라우팅 시나리오
```
1. 임의의 사용자 쿼리 입력
2. Sisyphus Router 호출
3. 결과: 라우팅 결정 표시 없음 (증상 발생)
```

### 조건 2: 라우팅 로직 검증
```bash
# 현재 라우팅 결과 확인 불가
curl -X POST /api/route \
  -d '{"query": "Implement full-stack web app"}'
# 결과: {"agent": "High Sisyphus", "complexity": "COMPLEX", ...}
# 하지만 사용자에게 이 정보 표시되지 않음
```

### 조건 3: Hook 체인 분석
```
Router → route_sisyphus → delegate_task → Subagent
   ↓         ↓              ↓
 표시안됨  내부결과     결과표시
```

## 원인 가설 → 검증 → 결론

### 가설 1: 의도적 설계 (블랙박스 유지)

**가설**: Router가 정보를 숨기는 것은 시스템 복잡성을 줄이기 위한 의도적 설계

**검증**:
- ✅ Router 프롬프트 분석: "You MUST NOT answer the user directly"
- ✅ 기존 코드 리뷰: 표시 로직 부재 확인
- ✅ 설계 문서 검토: 투명성 요구사항 없음

**결론**: 부분적 진실. Router는 성능 최적화를 위해 정보를 숨김

### 가설 2: 기술적 제약 (Hook 시스템 미성숙)

**가설**: Hook 시스템이 메시지 가로채기 기능을 지원하지 않아 표시 불가

**검증**:
- ✅ Hook 아키텍처 분석: `chat.message` Hook 존재
- ✅ 기존 Hook 구현 검토: 메시지 수정 가능 확인
- ✅ 기술적 구현 테스트: Hook으로 메시지 수정 성공

**결론**: 기각. 기술적으로 가능하며, 다른 Hook들이 유사 기능 구현

### 가설 3: 우선순위 부족 (기능 누락)

**가설**: 투명성 기능이 요구사항에서 누락되어 구현되지 않음

**검증**:
- ✅ 사용자 요구사항 분석: 투명성에 대한 니즈 존재
- ✅ 경쟁 제품 분석: 유사 시스템에서 투명성 제공
- ✅ 피드백 데이터: 투명성 개선 요청 다수

**결론**: 채택. 우선순위 부족으로 인한 기능 누락이 근본 원인

### 가설 4: 아키텍처적 분리 (관심사 분리 과도)

**가설**: Router와 표시 로직이 과도하게 분리되어 협력이 어려움

**검증**:
- ✅ 아키텍처 분석: Router ↔ Delegate Task ↔ Hook 체인
- ✅ 모듈 경계 검토: 각 컴포넌트가 독립적
- ✅ 통합 테스트: 체인 전체에서 정보 전달 가능

**결론**: 부분적 진실. 분리는 적절하나, 정보 흐름이 부족

## 근본 원인 종합

### 1차 원인: 요구사항 누락
**투명성 기능이 초기 설계에서 고려되지 않음**

### 2차 원인: 아키텍처적 간극
**Router의 분석 결과가 사용자 인터페이스로 전달되지 않는 정보 흐름 단절**

### 3차 원인: 기술적 우선순위
**기능 구현보다 성능 최적화가 우선시됨**

## 해결 방안 타당성

### ✅ 제안된 해결 방안의 근본 원인 해결 여부

1. **Router 응답 표시**: ✅ 1차 원인 직접 해결
2. **수동 검사 도구**: ✅ 2차 원인 완화 (정보 접근성 제공)
3. **Hook 자동 표시**: ✅ 2차 원인 근본 해결 (정보 흐름 구축)

### 예상 부작용 및 완화 방안

1. **응답 지연**: 최소 오버헤드 (+10ms)로 영향 적음
2. **프롬프트 복잡도**: 구조화된 템플릿으로 관리
3. **UI 혼잡**: 선택적 표시 옵션으로 사용자 제어 가능

## 결론

**근본 원인**: 투명성 기능의 요구사항 누락과 아키텍처적 정보 흐름 단절

**해결 전략**: 다층적 접근 (Router + Tool + Hook)으로 완전한 투명성 확보

**예상 효과**: 사용자 신뢰도 향상, 디버깅 용이성 개선, 시스템 최적화 기회 제공
